# Media validation key operations

The browser uploads image bytes directly to Supabase Storage. After authentication, the application server validates its `MEDIA_VALIDATION_KEY_ID` and Base64 HMAC key locally. It then checks that the caller owns an authorized `PENDING` upload and asks a narrowly scoped authenticated RPC to compare a random 256-bit challenge signature against the matching key in Supabase Vault. The challenge is bound to the media UUID and key ID. The RPC returns only a boolean; it never returns the key, secret value, or Vault error details. A missing or mismatched local/Vault pair fails closed before the Storage object is downloaded or decoded.

Before doing image work, the route uses its server-only Supabase key to call a service-role-only slot RPC. The user ID comes from the server's verified Auth user, and SQL rechecks that this user owns the authorized `PENDING` media intent before atomically applying the five-attempts-per-60-seconds limit and claiming one of two global verification slots. Browser-authenticated PostgREST callers cannot invoke the claim or release RPCs; the earlier authenticated signatures are removed by the server-boundary migration. The private database tables have no client grants. A slot has a random, request-specific 256-bit lease token, stored only as a digest in the database, and expires after 90 seconds (longer than the route's 60-second maximum). The route attempts to release it in `finally`, including after proof activation changes the asset to `ACTIVE`; expiration cleans up slots after process interruption. Quota/capacity exhaustion returns a bounded `Retry-After`; database errors fail closed.

The application server downloads only the caller's own object through the caller's JWT and public publishable key, never through a service-role bypass. It verifies the actual downloaded bytes and fully decodes them with Sharp, checks the real JPEG/PNG/WebP format, enforces the 100 MB and 40-megapixel ceilings, and signs a 60-second, one-use proof. For PNG, a bounded chunk-framing parser rejects an `acTL` animation-control chunk before the first `IDAT`; it also rejects a PNG that exceeds the pre-IDAT chunk-work bound. Sharp's `pages` check rejects animated WebP and other multi-page inputs. Malformed chunk framing continues to Sharp's fail-closed decoding path. The activation RPC checks the proof against the Vault key and exact pending asset row before making the object public. Missing configuration, an invalid proof, expiry, replay, or decode failure leaves the image private and pending.

## Provisioning

1. Apply the append-only `trusted_media_proofs_and_password_gate`, `media_verification_intent_rpc`, `media_verification_budget_and_key_preflight`, and `media_verification_slot_server_boundary` migrations in order to the intended Supabase environment. These migrations do not create or seed any secret. Either the migration or matching server route may be deployed first; verification fails closed until both are present.
2. Generate a fresh cryptographically random key of at least 32 bytes in an approved password manager or secret manager. Store its Base64 representation directly in the secret manager; do not put it in source control, SQL migrations, shell command arguments, tickets, logs, screenshots, or Hybrid artifacts.
3. Choose a non-secret key identifier containing only letters, numbers, dots, underscores, or hyphens. In Supabase Vault for that same project, create a secret named `yum-review-media-validation:<key-id>` whose value is the Base64 key. Vault keeps the database copy encrypted; the key-preflight and activation functions use the decrypted secret only for HMAC comparisons.
4. Add `MEDIA_VALIDATION_KEY_ID`, `MEDIA_VALIDATION_HMAC_KEY`, and a Supabase server key as `SUPABASE_SECRET_KEY` to the Vercel server environment for the matching deployment. The legacy `SUPABASE_SERVICE_ROLE_KEY` name is also accepted by the server helper. The key ID must exactly match the Vault secret suffix; the HMAC key is the same Base64 value. All three are server-only variables. Never use a `NEXT_PUBLIC_` name or put the Supabase server key in browser code. This media verification route uses the server key only for slot claim/release; intent lookup, Vault preflight, Storage download, and proof activation continue through the caller's JWT.
5. Keep Preview and Development separate from Production. Do not connect Preview to the production Supabase project. Use a distinct key in an isolated Supabase environment, or leave upload verification unconfigured there; the route then fails closed. Local development also needs its own local Vault secret and key pair.
6. Redeploy after changing Vercel environment variables. Verify uploads only with disposable accounts and images in the matching non-production environment before enabling the feature for users. Include a direct authenticated PostgREST call to both removed signatures and both service-role-only signatures in the runtime checks; each must be denied. The rate limit, global semaphore, release after activation, Vault access, Storage RLS, migration behavior, and image-decoder behavior still require runtime verification on a disposable local Supabase environment. Static code inspection does not prove those runtime gates; they remain unverified.

## Rotation and incident response

Proofs expire after 60 seconds. For planned rotation, briefly pause uploads, deploy the new `MEDIA_VALIDATION_KEY_ID` and key, add the corresponding Vault secret, then resume after both sides match. Remove the old Vault secret and environment value after the overlap window. A mismatched or missing pair intentionally prevents activation; it does not make pending objects public. If a key may have leaked, pause uploads, replace both copies, and review pending uploads before resuming.

The SHA-256 in the proof is over the exact stored bytes. `original_bytes` is claimed by the browser when it creates the upload intent; because bytes are sent directly to Storage, the server cannot independently recover the pre-optimization source size. The database binds that recorded value to the proof. By contrast, the server independently measures the downloaded stored-object byte count and the activation RPC matches it to Storage metadata.
